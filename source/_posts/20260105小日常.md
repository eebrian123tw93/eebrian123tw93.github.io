今天在升級 **live555** 套件，從 **2014 版升級到 2025 版**。  
整個問題的釐清與除錯過程，**前後大約花了 2 週時間**。

需求是在系統中新增一個功能：**使用 live555 的 `TaskScheduler`，每秒更新一次 shared memory 的值，讓其他 process 可以檢查這支 `wis-streamer` 是否仍然存活**。

剛完成到可以編譯並正常執行時，卻發現一個異常現象：  
 <!-- more -->
 **`TaskScheduler` 並沒有穩定地每秒執行一次**，有時甚至會延遲到 **10 秒** 才執行。

開始追 code 後發現，只要 **RTCP 那邊有註冊 scheduler**，延遲就會出現，而且行為相當隨機。  
為了降低變因，我後來簡化測試條件，只保留 **1 路串流、僅送 video**，此時延遲現象就沒有那麼嚴重。

接著我比對了 **新版與舊版 scheduler 的實作差異**，也深入研究了它的排程機制。表面上看起來差異不大，理論上不應該造成這種問題。  
直到我開始 **列印 scheduler 內部儲存的剩餘時間**，才發現一件很詭異的事：**竟然出現負值時間**。

我進一步檢查了時間計算中可能發生借位的地方，邏輯上也沒有問題。更奇妙的是，**只要我多加一行 `printf`，行為就恢復正常了**。

詢問 GPT 之後，才被點醒：**這很可能是編譯器最佳化（compiler optimization）造成的未定義行為被掩蓋或放大**。  參考{% post_link  "編譯器最佳化導致問題（UB 筆記）" %} 和 {% post_link  "Strict Aliasing Rule Undefined Behavior" %}
在釐清問題與風險的過程中，**另一個實際且有效的解決方式，就是主動詢問資深同事，確認是否曾遇過類似情境或已知 live555 在新版下的潛在陷阱**，能避免在錯誤方向上耗費過多時間。

結論就是：  
**以後遇到這種詭異問題，除了自行追 code，也要及早確認編譯參數、使用 `gdbserver`，並適時向資深同事請教，才能更快找出真正的原因。**
