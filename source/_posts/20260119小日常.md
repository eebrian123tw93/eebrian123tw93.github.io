今天在工作時又遇到一個蠻棘手的問題。

在和其他家廠商串接 NVR 的時候，RTSPS 一直怎麼都串不起來。第一個直覺當然是「抓封包來比對」，但問題來了：它是 **RTSP over TLS**，整個連線流程都是加密的，導致我根本看不到實際的 RTSP 封包內容。

一開始有查到網路上的作法，是用 **Wireshark 解 HTTPS / TLS** 的方式：  
透過設定 `SSLKEYLOGFILE` 環境變數，讓應用程式在 TLS 握手時把 session key dump 到指定的檔案，再讓 Wireshark 讀這個 key log 來解密封包。
 <!-- more -->
 
但這條路很快就卡關了，原因很現實：

- **只有特定支援的程式**（例如某些瀏覽器、libssl 有開啟功能的應用）才會把 key dump 到 `SSLKEYLOGFILE` 可參考{% post_link  "wireshake tls 解包 教學 使用 SSLKEYLOGFILE" %}
- NVR 是第三方的，完全無法控制
- openRTSP 雖然可以自己編譯，但還得額外實作把 TLS key dump 出來的機制，成本太高  
    → 這條路基本上先放棄。
    
後來再問 GPT，得到另一個方向：  
可以用 **PolarProxy** 去代理 **322 port（RTSPS）**，藉由 MITM(中間人攻擊) 的方式把 TLS 解開。  
這個方法對 **TCP 流量是可行的**，但如果牽涉到 **UDP（例如 RTP over UDP）**，PolarProxy 就完全無法處理。 可參考{% post_link  "wireshake tls 解包 教學 使用 PolarProxy" %}

再繞了一圈後，發現一個關鍵點：  
NVR 在拉流之前，**一定會先透過 ONVIF 去拿 RTSP URI**，而 ONVIF 本身是走 **HTTP / HTTPS（80 / 443）**。

於是策略就變成：
- 用 **Nginx 代理 TCP 80 / 443**
- 把 ONVIF 流量導到可控的中介層
- 進而影響後續 RTSPS 的連線行為

![](/images/20260126154857.png)

結果這樣一繞，**最後成功把 RTSPS 的封包解開來看**，也終於能實際比對雙方在 RTSP/TLS 流程上的差異。

整體來說是個繞路但有效的解法，也再次驗證：

> 有時候解不開資料流本身，就要從「先看是誰給它連線資訊的。」下手。
