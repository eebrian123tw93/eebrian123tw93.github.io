今天在與某家廠商串接 NVR 時，遇到一個多播斷線的問題，整理如下。

在串接 **RTSPS** 的過程中：
- **單播 RTSP over SSL over TCP**：已成功打通
- **單播 RTSP over SSL over UDP**：也已成功
- **多播**：卻會在約 **30～40 秒後斷線**

因此先嘗試改用 **不加密的 RTSP（非 RTSPS）**，但多播仍然會斷線，問題依舊存在。
 <!-- more -->
 
一開始以為是 **FPS 掉落** 導致 Client 主動斷線，但使用 **VLC 播放多播串流** 時一切正常，也沒有斷線情況，因此初步排除 FPS 問題。

接著發現一個更奇怪的現象：
- **只有一個 NVR client 連線時** → 約 30～40 秒會斷線
- **同時有兩個 client（一個 VLC + 一個 NVR）連線時** → 不會斷線
因此決定開始攔封包分析。

---

### 第一階段分析：RTCP RR？

最初懷疑是 **RTCP Receiver Report（RR）沒有送出** 導致斷線，因為在 **live555** 裡有一個 `RRHandler` 機制，只要收到 RR，就會更新 scheduler，避免 session 被判定為 timeout 而切斷。

但實際攔封包後發現：
- **VLC 在多播時也沒有送 RR**
- 卻依然不會斷線

因此這條線索行不通，分析一度卡關。

---

### 重新思考方向：RTSP Liveness 機制
重新思考後，改去攔 **單播 UDP 為何不會斷線**，結果觀察到：
- **NVR 在單播 UDP 時，會定期送出 `OPTIONS` RTSP request**

進一步回頭追 **live555 原始碼**，發現：
- `noteLiveness()`
    - 只要 **收到 RTSP 封包（例如 OPTIONS、GET_PARAMETER）**
    - 就會被呼叫，用來更新 session 的存活時間

再對照 **VLC 的多播行為**：
- VLC 在多播 UDP 時，會定期送出 **`GET_PARAMETER`**
    
但 **NVR 在多播時完全沒有送任何 RTSP keep-alive 類型的封包**，導致：
- server 無法得知 client 還活著
- 超過 timeout 後就主動清除 session
- 因此在約 30～40 秒後斷線

---

### 結論與解法

**根本原因**：

> NVR 在「多播」模式下，沒有送出任何可讓 server 判定 client 存活的 RTSP 訊號（如 OPTIONS / GET_PARAMETER）。

**暫時解法**：
- 將 server 的 session timeout 30秒**拉長到 5 分鐘**
- 讓 server 仍能定期清除不必要的連線，同時避免正常多播過早被斷線
